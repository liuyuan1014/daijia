# 代驾项目 vs 工业园区无人机协作调度平台 技术对比分析

## 0. 编写说明
- **目的**：对比原始代驾项目与当前无人机协作调度平台在技术架构、业务流程、数据与规则、运维安全等方面的差异，便于汇报、面试与背景阐述。
- **信息来源**：
  - 《代驾项目面试文档》
  - 《工业园区无人机协作调度平台技术文档》
  - 相关代码结构与配置清单
- **适用场景**：背景说明、技术答辩、方案评审、迁移评估。

## 1. 项目定位与业务场景

| 维度 | 代驾项目 | 无人机协作调度平台 | 核心差异 |
| --- | --- | --- | --- |
| 目标用户 | C 端客户、代驾司机、运营方 | 工业园区运维、飞手、任务申报部门、运营中心 | 面向 B2C vs B2B 场景，参与角色差异大 |
| 核心诉求 | 夜间代驾、订单撮合、支付结算 | 园区物料配送、巡检、应急响应、协同调度 | 场景复杂度、任务种类、多终端协同 |
| 终端形态 | 客户 APP、司机 APP、运营后台 | 微信小程序（飞手 & 任务申报）、运营大屏（Web） | 无人机平台以小程序 + 大屏为主，轻端驱动 |
| 生态合作 | 微信支付、腾讯 AI OCR/人脸 | 腾讯 AI OCR/人脸、地图、气象、XXL-Job 等 | 无人机项目第三方集成维度更广 |

## 2. 整体技术架构与模块

### 2.1 架构共性

- 均基于 **Spring Boot 3.0.5 + Spring Cloud Alibaba** 的微服务体系。
- 使用 **Nacos** 做注册/配置中心，**OpenFeign** + **LoadBalancer** 进行服务调用。
- **Redis** 作为缓存、分布式锁基础组件。
- **RabbitMQ/RocketMQ** 作为事件总线（订单/任务状态驱动）。
- 引入 **Drools** 规则引擎，实现计费、奖励等可配置规则。
- 全链路日志、链路追踪、监控告警体系（Actuator、Prometheus、Sleuth、ELK 等）。

### 2.2 模块拆分对比

| 类型 | 代驾项目 | 无人机项目 | 说明 |
| --- | --- | --- | --- |
| 基础服务 | service-driver, service-customer, service-order, service-payment, service-map, service-rules, service-dispatch, service-system | service-uav-pilot, service-task-requester, service-delivery-task, service-scheduling, service-industrial-map, service-energy-rules, service-billing, service-event, service-incentive, service-system, gateway-server | 两者均遵循领域划分，后者覆盖更多垂直域（事件、能源、激励） |
| 客户端 | 客户 APP、司机 APP、运营后台（Vue3/Vite） | 飞手小程序、任务申报小程序、运营大屏（Vue3/Vite） | 无人机平台强调轻端 + 可视化大屏 |
| 公共组件 | common-log、common-util、service-util、spring-security 等 | 一致 | 基础设施复用 |
| Infra/工具 | RabbitMQ、Redis、MySQL、MongoDB | RocketMQ/RabbitMQ、Redis、MySQL、MongoDB、Elasticsearch、Prometheus | 无人机引入 ES、Prometheus 提升可观测性 |

### 2.3 改造后核心技术差异（重点）

| 技术维度 | 代驾项目（原实现） | 无人机平台（当前实现） | 差异侧重点 |
| --- | --- | --- | --- |
| 终端形态与发布 | Vue3 + Vite 的运营后台、司机/客户原生 App | 可直接沿用原“运营后台 + 双端 App”模式；当前版本将司机/客户 App 换成飞手/任务申报小程序，本质仍是双端 + 后台的三端结构，接口协议不变 | 从记忆角度可完全套用代驾终端架构，如需小程序仅是壳层替换，前后端交互范式一致 |
| 调度引擎 | Redis 去重 + 司机抢单/派单策略 | 在原调度框架上扩展 XXL-Job 定时批调度，沿用 Redis 去重与抢单机制，仅把评分因子替换为电量、载荷、天气等无人机指标 | 认知方式不变（Redis + MQ + 抢单），只是评分模型换成无人机场景参数 |
| 规则引擎实践 | Drools 处理计费、司机激励，加价模型较固定 | 继续使用 Drools，同一套请求/响应模型与 Global 写法，增加能耗、审批、预算等规则文件 | 原规则引擎代码全部复用，只新增规则包与字段，运营规则管理方式保持不变 |
| 数据与存储 | 结构化数据主导：MySQL + Redis，少量 MongoDB | MySQL + Redis 架构原样继承，仅追加航迹 MongoDB 与告警 Elasticsearch 作为补充数据源 | “主库 + Redis” 核心策略不变，新增存储属于可选扩展，原开发习惯无需改变 |
| 可观测与告警 | Actuator + Prometheus + ELK，聚焦订单/支付健康度 | 继续用 Actuator/Prometheus/ELK，只在 Grafana/大屏里增加无人机指标，SkyWalking 配置与代驾一致 | 监控链路、告警规则模板均复用，额外指标当作新面板即可，SRE 习惯完全沿袭 |
| 安全与合规 | JWT + 接口签名，司机人脸识别，支付风控 | Spring Security + JWT 框架原样保留，增加企业微信登录、多因子认证、人脸/工牌 OCR；审计日志仍走原 LogAspect | 安全管控仍靠既有组件，只是在相同流程里加校验点，开发接口/鉴权逻辑一致 |

**补充说明：**
1. 终端架构调整后，原本前端的实时逻辑（抢单、确认、异常反馈）全部后移至 `service-*` 微服务与 MQ 流转，小程序仅承担展示与指令入口。
2. 调度、规则、数据三项是改造后的“技术分水岭”：需要跨团队（算法、数据、安全）协同，且对基础设施提出更高要求。
3. 可观测性与安全治理成为工业场景必备，形成“任务—设备—飞手—告警—审计”的闭环链路。

### 2.4 继承与一致性策略（确保记忆负担一致）

| 维度 | 原代驾项目实现 | 无人机平台延续做法 | 一致性要领 |
| --- | --- | --- | --- |
| 微服务结构 | 父级 pom 聚合 common、service、web、gateway | 保持同级目录结构，仅将业务模块命名映射到无人机域（如 service-driver → service-uav-pilot） | “模块职责 = 代驾同名服务 + 无人机语义” 的思维方式 |
| 公共依赖 | `common-log`、`common-util`、`service-util`、`spring-security` | 完整复用，无新增公共模块 | 公共层不用重新记，照旧可引用 |
| 配置中心 | Nacos 命名空间按环境划分，模块独立 yaml | 继承同样命名规则与配置拆分，仅更新业务字段 | “路径不变，仅内容变” |
| 接口调用 | OpenFeign + Sentinel；统一异常、日志链路 | 保留原拦截器、Feign 模板、异常体系 | 调用链与代驾一致，参数换领域对象 |
| 规则编排 | Drools 全局变量 + Request/Response Fact | 相同编程模型，仅更换规则文件与事实对象 | 记忆“先设 global，再 insert fact” 即可 |
| 事件驱动 | RabbitMQ 交换机、路由键常量集中管理 | 保留 `MqConst` 常量结构，扩展任务相关 routing key | 事件命名沿袭 `业务动作` 模式 |
| 安全体系 | Spring Security + JWT + 自定义注解 | 沿用原登录/鉴权框架，只增加企业微信与多因子实现 | 记住“加了前置认证节点”即可 |
| 运维套路 | Actuator、Prometheus、Grafana、ELK、自建 dash | 原监控链路保留，新增的仅是指标项 | 记忆“面板结构同样位置，多了设备指标” |

> **记忆技巧**：把无人机平台看成“代驾项目的业务域替换版”，技术骨架、编程范式、运维链路 80% 与原项目一致，只需在脑海中将“司机/客户/订单”替换成“飞手/任务/无人机”，即可快速切换。

## 3. 业务流程对比

### 3.1 主干流程

| 环节 | 代驾项目 | 无人机项目 |
| --- | --- | --- |
| 任务/订单发起 | 客户 APP 下单，选择起终点 → 预估费用 | 部门通过任务申报小程序提报，系统或人工审批 |
| 调度派单 | service-dispatch 根据距离/评分等派单；司机可抢单 | service-scheduling 综合电量、距离、载荷、天气等评分，多策略并存（自动派单、飞手确认、异常重分配） |
| 执行与监控 | 司机到达 → 开始代驾 → 结束服务 | 飞手扫码出库 + 人脸验证 → 无人机飞行，遥测数据实时回传大屏 |
| 结算与分账 | Drools 计费 → 微信支付 → 分账至司机 | Drools 费用 + 能耗 + 激励 → service-billing 结算 → 分账/预算控制 |
| 异常处理 | 司机爽约、支付失败、投诉等 | 天气异常、无人机故障、飞手失联、任务延期等，事件服务 + 调度重分配 |

### 3.2 状态机/生命周期

- **代驾订单状态**：等待接单 → 已接单 → 司机到达 → 代驾中 → 完成 → 已支付。
- **无人机任务状态**：待审批 → 待调度 → 待执行 → 执行中 → 异常处理 → 完成回执 → 结算 → 归档。
- 无人机任务在纵向上增加审批、调度、监控、结算多个环节，状态机更复杂，对异常链路定义更细致。

## 4. 核心算法与规则差异

| 维度 | 代驾项目 | 无人机平台 |
| --- | --- | --- |
| 调度/派单 | 距离优先 + 司机评分 + 接单范围；Redis 去重；Redisson 分布式锁 | 加权评分模型（距离、电量、载荷、飞手评分、故障率、天气）；XXL-Job 批调度；MQ 推送附近飞手 |
| 计费规则 | 起步价 + 里程费 + 时长费 + 夜间加价，Drools 实现 | 任务类型、时间窗口、能耗、夜航、激励等多维规则；支持灰度发布、版本回滚 |
| 激励机制 | 司机完单奖励、好评奖励、活跃奖励 | 飞手绩效、积分奖金、夜航激励；Drools + Redis 高频数据 |
| 风控/安全 | 人脸识别、OCR、支付风控 | 人脸识别 + 工牌 OCR + 活体；任务审批 + 调度安全阈值 + 轨迹回放；天气 API 联动 |

## 5. 数据模型与存储

### 5.1 数据设计差异

| 项目 | 代驾 | 无人机 |
| --- | --- | --- |
| 主实体 | driver_info、order_info、payment_info、customer_info | uav_info、uav_pilot、task_info、task_status_log、task_trajectory、billing_record、rule_snapshot、event_log |
| 数据量特征 | 高并发短时订单，结构化数据为主 | 长周期任务、遥测数据（MongoDB）、日志与告警（Elasticsearch） |
| 分库分表 | 订单按时间或城市分表；用户按 ID 哈希 | 任务/航迹按园区/时间分片；大量时序数据入 MongoDB/ES |
| 缓存策略 | 会话、司机状态、订单状态、分布式锁 | 任务队列、无人机状态、附近飞手缓存、延迟队列 |

### 5.2 数据一致性

- **共同点**：关键链路使用 MQ + 最终一致性；幂等设计；分布式锁控制。
- **差异点**：无人机平台更强调状态机 + 事件驱动（任务异常重分配、告警闭环），对一致性保障链路更长。

## 9. 技术难点对比

| 分类 | 代驾项目 | 无人机项目 |
| --- | --- | --- |
| 分布式事务 | 支付成功涉及订单、账户、奖励 → MQ + 补偿 | 任务结算涉及 Drools、费用、能耗、激励、多表写入 → MQ + 状态机 |
| 调度复杂度 | 司机抢单，高峰期锁竞争 | 多无人机/飞手组合评分，多策略并发，天气/禁飞约束 |
| 规则引擎 | 费用规则、司机激励，主要针对订单 | 费用 + 能耗 + 激励 + 审批 + 安全阈值，规则组合复杂 |
| 数据压力 | 高并发单点订单，主要结构化数据 | 遥测、航迹、高维告警数据，需多存储组合 |
| 安全与合规 | 支付、身份认证、风控 | 工业安全、飞行法规、任务审批、操作审计 |
| 可视化 | 订单/运营后台 | 实时航迹、告警大屏、无人机状态可视化 |

## 10. 迁移与复用建议

1. **架构层面**：两者均为 Spring Cloud Alibaba 微服务体系，公共组件（common-*/service-util/spring-security）可直接复用。
2. **规则引擎**：Drools 使用经验可迁移，但无人机平台需更复杂的规则组合与灰度发布机制。
3. **消息与缓存**：Redis + MQ 的幂等、去重、延迟队列实践可继续沿用，需增强对事件链路的监控。
4. **安全体系**：扩展 JWT + OAuth2，多因子认证经验可以基础化后应用于无人机场景。
5. **运维监控**：原有的 Prometheus/Grafana、ELK 体系可以扩展业务指标，重点补充任务/设备维度监控。
6. **流程再造**：代驾项目的订单状态机经验可用于定义无人机任务状态，但需增加审批、异常、回放环节。

## 11. 结论与沟通要点

- **定位差异**：代驾项目服务 C 端用户，以实时订单履约为核心。无人机平台服务工业园区，强调多任务协同、安全合规、可视化监控、策略调度。
- **技术演进**：无人机平台继承代驾项目的微服务与规则引擎架构，扩展了任务调度、事件驱动、能源计费、告警体系等能力。
- **关键亮点**：
  - 多智能体调度与评分算法（距离、电量、载荷、天气、故障率等）。
  - Drools 规则库深入应用（费用、激励、能耗），支持灰度发布。
  - 实时可观测大屏 + Prometheus/Grafana/SkyWalking 组合。
  - 工业级安全合规体系（多因子认证、操作审计、轨迹回放）。
- **可复用价值**：公共组件、规则引擎实践、事件驱动架构、缓存/幂等策略、监控体系均可跨项目复用。
- **沟通建议**：在对外交付或面试时，强调从 C 端代驾转向 B 端工业调度的跨场景能力，突出“微服务底座 + 规则引擎 + 调度算法 + 工业安全”综合方案经验。
